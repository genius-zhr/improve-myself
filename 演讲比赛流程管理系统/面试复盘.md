## Q1 整体流程

**题目**：用户选「1 开始比赛」，系统依次做了哪些事？（按第一轮 / 第二轮组织）

**我的回答**：比赛分两轮。第一轮把 12 人打乱顺序平分成两组，每组比赛后按评委打分和编号顺序决出前 3 名进晋级名单，两组共 6 人；第二轮这 6 人不再分组，直接比赛，按成绩和编号排定冠亚季军，输出结果并把冠亚季军存入历史信息。

**评委点评：通过（B+）**。骨架正确，但漏了 3 个实际发生的细节：
1. **每轮结束成绩都要存盘**——第一轮、第二轮都会把名单 + 两轮成绩写回 `speaker.txt`（`saveRecord`）。
2. **第二轮开始前要重新抽签**——6 名晋级者不是直接比，而是先打乱出场顺序（`drawOrder`）。
3. 打分规则只是一带而过——10 位评委随机打分、去掉最高最低、8 个取平均。

> 结论：对"赛制"理解到位，对"系统每一步做了什么"还要更熟。

## Q2 设计决策

**题目**：选手存 `map<int, Speaker> m_speakers`，但抽签、分组、晋级名单里只存 **int 编号**，不存 Speaker 对象。为什么？好处是什么？

**我的回答**：用编号定位、排序比姓名方便；只有关键信息用 map，其他用 int 存编号方便操作。好处是省内存，不拷贝没用的信息。

**评委点评：及格（C+）**。结论对，**理由错**：
1. **"编号方便排序"偏了**——排序比的不是编号，是成绩；编号只在同分时打破平局。
2. **"省内存"只是次要好处**，不是关键。
3. **真正原因：避免"拷贝过期"，保证数据只有一份**。看 `contest()` 的执行顺序：

   ```
   m_group1.push_back(编号)   ← 先分组（此刻还没打分）
   score(1, m_group1)         ← 后打分，成绩写进 m_speakers
   promoteTop(3, m_group1)    ← 再排名
   ```

   如果 `m_group1` 装的是 Speaker **拷贝**，这些拷贝在"分组那一刻"就生成了，当时成绩还是 0；之后 `score()` 把新成绩写进 **map 里的那份**，vector 里的拷贝**还是旧成绩**。排名时比一堆 0，全乱。
   而存**编号**，排名时 `m_speakers[id].getRound1()` **现查**，每次都是最新成绩。

> 一句话：**不用拷贝，是因为成绩在比赛过程中会变，拷贝会把"旧成绩"冻结下来。** 这就是单一数据源（single source of truth）——vector 只是"谁上场、什么顺序"的名单，不复制数据。

## Q3 STL：sort + lambda

**题目**：解释下面这段 `promoteTop` 里的排序代码：

```cpp
sort(group.begin(), group.end(), [this](int a, int b) {
    double sa = (m_round == 1) ? m_speakers[a].getRound1() : m_speakers[a].getRound2();
    double sb = (m_round == 1) ? m_speakers[b].getRound1() : m_speakers[b].getRound2();
    if (sa != sb) return sa > sb;
    return a < b;
});
```

1. 这段代码在干什么？
2. 第三个参数是什么？为什么 `sort` 能接收它？
3. 为什么必须写 `[this]`？

**我的回答**：
1. 自定义排名规则，避免成绩相同的情况。
2. 第三个参数本质是一个函数对象，只是没名字，在参数列表里临时定义；`sort` 会通过括号触发它内部的 `operator()` 重载，作用和一个函数名相同，所以能接收。
3. `[this]` 是指向这个类对象的指针，只有这样才能访问类内部的数据。

**评委点评：B+**。
- **第 2 问（最好，基本满分）**：准确抓住了 lambda 的本质——编译期变成一个隐藏的类，`(...)` 就是它的 `operator()`，`sort` 像调用函数一样调用它。
- **第 3 问（核心对，一个小误会）**："`[this]` 是 this 指针、用于访问成员"——正确。但"不写会访问到未定义数据"**不对**：不写 `[this]` 是**编译错误**，lambda 作用域里根本看不到 `m_speakers` / `m_round`，直接编译不过，轮不到运行。
- **第 1 问（答偏一半）**：这个 lambda 的主业是定义排序规则——**按"当前轮次"的成绩从高到低排；只有成绩相同时，才用"编号小在前"兜底**。我漏掉了关键的三元表达式 `(m_round==1)?getRound1():getRound2()`——同一个排序函数要服务两轮比赛，先看 `m_round` 决定比哪个成绩。同分按编号只是平局兜底，不是主旨。

> 心得：以后写比较器要先问自己——"我在定义什么顺序？"

## Q4 实战 bug（晋级名单没清空）

**题目**：第二轮结束后显示 9 个人、名次乱、存档错。根源是 `m_promoted` 第二轮没清空（第一轮 6 人 + 第二轮 3 人 = 9）。修复是第二轮 `promoteTop` 前加 `m_promoted.clear()`。**为什么 `clear()` 是安全的？会不会把第一轮晋级的 6 人弄丢？第二轮靠什么找到这 6 人？**

**我的回答**：清空之前抽签已经把晋级者赋值到了 `m_order`，第二轮比赛靠的是 `m_order`。所以 `m_promoted` 从第一轮到第二轮只是临时数据存储器，存完用完丢掉不会造成影响，反而避免 bug。也可以完全把它当临时容器，另写一个容器存冠亚季军。

**评委点评：A（接近满分）**。抓住了最关键的一句：**"清空之前抽签已把 6 人复制进 `m_order`"**。把逻辑链理顺：

```
第一轮结束：m_promoted = [6 人]
第二轮开始：
  drawOrder()  →  m_order = m_promoted（6 人编号复制进 m_order，再打乱）
  contest()    →  score(2, m_order)      ← 比赛靠 m_order
              →  m_promoted.clear()      ← 此时 m_promoted 里的 6 人已"用完"，可安全丢弃
              →  promoteTop(3, m_order)  ← 前 3 名又写回 m_promoted
```

补充一层理解：`m_promoted` 在两轮里**语义不同**——第一轮后是"6 名晋级选手"，第二轮 `clear()` 后变成"3 名冠亚季军"。`showScore(2)` 和 `saveResult()` 都靠第二轮后的 `m_promoted`。`clear()` 是那个**语义切换点**。

## Q5 文件操作

**题目**：

```cpp
if (!file.is_open() || file.peek() == EOF) {
    m_fileIsEmpty = true;
}
```

1. 两个条件各自对应什么情况？
2. 只保留 `is_open()` 会漏掉什么？
3. 为什么用 `peek()` 而不是 `eof()`？

**我的回答**：① 前者管文件不存在，后者管文件为空。② 空文件会被误判为 false，导致后续"查看历届"输出一片空白。③ `eof()` 必须读到一次错误数据才返回 true，`peek()` 能提前预判是否为空。

**评委点评：A**。三点全对。补充：`peek()` 是"只看不动"，不消费流里的数据，判断完之后 `getline` 还能正常从第一行开始读。

## Q6 边界情况

**题目**：
- 场景 A：`speaker.txt` 被整个删除，启动程序会怎样？
- 场景 B：`speaker.txt` 只有 5 行，选「开始比赛」会怎样？注意 `contest()` 里 `for(int i=0;i<6;i++) m_group1.push_back(m_order[i]);`，如果 `m_order` 没有第 6 个元素呢？

**我的回答**：场景 A 会自动生成 12 个虚拟数据，能完整跑一遍，但内部数据无意义。场景 B 分组时会让不存在的数据也生成一份、数据为 0，打分赋值会影响排名、穿插"无名"选手，但总归不会崩。

**评委点评：B-**。场景 A 正确。场景 B **方向摸到边，机制说错，且有一个危险结论**：
- **对的部分**：会出现"无名"选手——这个洞察很准。来源是 `score()` 里的 `m_speakers[id]`，`map` 的 `operator[]` 在 key 不存在时会**自动插入一个默认选手**（姓名空、成绩 0）。
- **错的部分 1**："分组会创建一份 0 数据"不对。真正发生的是 `m_order[i]` 越界——`std::vector` 的 `operator[]` **不做越界检查**，只是按地址读内存，读到的是**垃圾**（可能是 0、乱数、甚至不可读内存）。
- **错的部分 2（最危险）**："不会崩"不成立。越界访问是**未定义行为（UB）**，可能得到垃圾值，也可能直接段错误。这次没崩不代表可靠——这是"跑十次崩一次"的隐性 bug。出现的"无名选手"，本质是**垃圾编号被传进 `score()`，`operator[]` 把它插成了幽灵选手**——运气好而已，不是设计好的行为。

> 真相：代码**硬性假设正好 12 人**（`m_order[0]`~`[11]` 全要取），但这个假设**没有任何检查**。数据不是 12 人就是越界 UB——可能崩、可能出幽灵选手，全看运气。
> 要建立"越界 = 未定义行为，不能赌它不崩"的意识。

## Q7 改进方向

**题目**：假设要加分、要拿得出手，这个系统还值得改什么？（至少 2 条）

**我的回答**：
1. 目前选手是固定的，没有**增删改查**，可以加上并实时修改文件数据。
2. 像 Q6 说的，**报名人数不足时设定判断，人数不够就不执行**。

**评委点评：A-**。两条都是真改进。补充：第 2 条的**本质不是"拦一下"**，而是把代码里写死的 `6`、`12` **参数化**——比如 14 人报名，`for(int i=0;i<6;i++)` 这种死数字就又崩了。真正的修法是让分组逻辑**按实际人数算**（如对半分），而不是靠"恰好 12 人"。

**评委补充的改进建议**：
1. **魔法数字 → 常量**：`12`、`6`、`3`、`10`、`60`、`100` 改成 `constexpr int`（如 `kPlayerCount`、`kJudges`），代码质量观感立刻不同。
2. **修 `showRecord` 的崩溃隐患**：`m_speakers.find(id)->second` 没先判断 `find() != end()`。如果 record.txt 被手改坏、引用了不存在的编号，`->second` 解引用 `end()` 迭代器又是 UB，直接崩。修法：先 `auto it = m_speakers.find(id); if (it != end()) 用 it->second;`
3. **随机引擎提为成员**：现在 `drawOrder`、`score` 每次调用都新建 `mt19937`。可以提成 `SpeechManager` 的成员，全程只用一台引擎，随机性更稳更专业。
4. **成绩固定两位小数**：`fixed << setprecision(2)`，答辩演示观感好很多。
